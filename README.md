## 智能脚本 V4：危机恢复与战役执行

开局修订 `crisis-campaign-opening-2` 修正了探索收益遗漏、500日殖民被短期粗评淘汰、方案落选缓存阻止后续经营，以及未知星系中心巡逻引发接触战的问题。预测不再把未下单舰船计为已实现价值；16轮隔离开局已验证实际扩张，长期强度仍以实赛观察为准。

新建局默认 **V4 标准档**，保持 5.4 规则与 48 动作。V4 增加运行设施封存与岗位组合、连续缺口和恢复预测；战争按实际战损、对手失分与可兑现控制收益比较，取消固定优势比例和准备奖励。集中舰队先集结再协调进军，清理过期任务，无关造舰不再刷新战役进度。

标准档最多 12 个军事方案，深度档 32 个，各比较三种确定情景；情景不是胜率。沿用持久化多核规划池与现有缓存，不扩大线程池。硬件只影响耗时，深度档显式增加搜索量。对未知敌军与外国得分不作精确假设，不保证强于模型。详见 [V4 策略说明](ADAPTIVE-V4.md)。

## 智能脚本 V3：组合规划与持续经营（保留）

可手动选择 **`adaptive-v3`**。V3 保持规则 5.4、48 条动作和本方情报边界；模型请求和 token 为 0。`legacy`、V1、V2 及旧档行为保留，不自动升级现有比赛。

| 搜索档位 | 候选 | 分支宽度 | 组合深度 | 草稿评估 | 详细预测 |
|---|---:|---:|---:|---:|---:|
| 标准 | 256 | 4 | 3 | 256 | 48 |
| 深度 | 512 | 8 | 4 | 1024 | 128 |

V3 重新比较每个行动前缀，保留竞争组合与等待；预测包括福利未兑现、凝聚力低谷、治理 Q 和折算社会资产。LRS 根据未来实际运营后的覆盖计价，战役记忆参与目标、集结和资金取舍。确定预测不假设战争胜利，成功履责单列条件情景。

本地修复 `whole-turn-1` 将组合搜索与剩余经营分开：预测用完仍可安排经校验的独立行动，保持原预算及48动作上限；提高待遇检查全部预测窗口，统一设施估值，提前比较边境防御并抵扣可按期到达的在建军备。界面新增停手原因及未执行机会。本轮仅做必要检查与一场四方完整观察，不重跑性能基准；见[修复观察报告](TESTING-ADAPTIVE-V3-REPAIR.md)。下文性能数值属于修复前历史测量。

修复后唯一四方局完成120轮：翠星V3以11785分获胜，每轮平均6.62条动作、无空计划，426条动作来自后续经营；另一V3席位晨曦仍被淘汰。规划中位数26.62秒、p95为75.26秒，性能仍慢，关键预测预算与弱势恢复仍有缺口，不能据此宣称V3全面强于V2。未发布、未部署。

**高性能设备可以显式选择深度档。** 自动计算线程预算为 `min(64, 逻辑处理器数−2)`，其中最多 8 个协调线程，其余并行处理候选、草稿和预测。`computeWorkers=0` 提供串行参考。缓存默认不超过 **8192 MiB** 或可用内存的 25%，按需使用；缓存预算不等于进程 RSS 上限。线程、缓存不影响世界哈希，搜索档位会影响决策并进入存档和哈希。

性能指标分开记录规划、预演、预测、排队、CPU、RSS、缓存及主线程延迟。32 逻辑核、约 64GB 机器的三个固定快照中，热运行标准档中位数为 **14.81 秒**，深度档 **39.60 秒**；同档串行分别为 76.15／245.04 秒，动作与记忆哈希一致。深度档 **未达到 10–20 秒目标**，八方第100轮约98.79秒、RSS最大采样约8.6GiB。主要瓶颈仍是前缀候选重算、预演及消息复制；不是线程越多就线性加速。

**当前为未发布的本地实现。** 两场固定 V3 深度／V2 对照均运行至120轮、由V2获胜。V3仍有早期福利风险、投资节奏慢及战役兑现不足，不能宣称更强或建议替代稳定V2；详细证据和未达成项见报告。原真实比赛与8787服务未推进。

## 智能脚本 V2：保留的基线与历史实测

**`adaptive-v2`** 继续可选，保留 `adaptive-v1` 和 `legacy`。恢复旧档不切换策略，缺少版本字段的旧脚本档继续使用 legacy。以下为 V2 已发布的实现与历史测量；游戏规则仍为 **5.4**，每方每轮最多 **48条实际动作**，模型请求与 token 均为0。

- **建筑与运营一起比较**：建设、调岗、封存、重启使用相同岗位和供应条件。LRS按两跳新增覆盖与军情需求计价，重复覆盖不重复获益；界面明确地表／轨道、预留槽位、运营比例和停工原因。
- **战略采用共同口径**：四条文明路线比较当前成本与条件收益，不把降低福利节省算成军国制度增益。征服准备可先于军力成熟，正式宣战仍检查新鲜军情、1.3倍进攻门槛、通行和留守。
- **有界、可追溯规划**：所有行星先参加筛选，最多256个候选、24份详细预测；只使用本方知识，全部势力成功后共同提交。失败重试按相关条件判断，库存变化不会解除旧施工情报失败。
- **三层线程分别显示**：规划 worker 并行处理各国，预测 worker 处理同一草稿前缀下的独立经济方案，模拟 worker 处理世界局部计算；增加模拟线程不等于加快规划。

### CPU、内存与实测性能

自动规划线程不超过势力数和8；预测使用剩余预算。规划与预测合计最多16，并按逻辑处理器数保留至少2个给主线程及系统；低核机器可自动退回无规划 worker 模式。`planningWorkers`、`forecastWorkers` 是运行参数，不进入世界哈希；两者均0提供参考模式。模拟线程由独立的 `WORKERS` 控制，各阶段并非同时持续满载。

持久化线程池减少启动开销；增量草稿、轮内静态比较缓存和裁剪后的预测输入减少重复计算与复制。每国最多64个草稿缓存条目、24份详细预测，前缀变更使依赖结果失效。界面和审计展示候选、复制、静态比较、预测、校验、排队和保存耗时，以及内存与缓存指标。

在 **AMD Ryzen AI MAX+ 395、32逻辑处理器、约64GB RAM** 的三个固定中后期快照上：

| 模式 | 规划中位数 | 样本p95 | 平均忙核心 | 观测峰值RSS |
|---|---:|---:|---:|---:|
| V1 | 21.52秒 | 49.57秒 | 1.06 | 1533MB |
| V2无worker参考 | 22.16秒 | 30.39秒 | 1.07 | 622MB |
| V2并行 | **5.40秒** | **6.58秒** | **7.43** | 2799MB |

V2并行中位耗时下降 **75.6%**，三个快照的动作、记忆和摘要一致，未降低搜索预算。样本包含冷启动，p95仅来自三个快照；RSS来自同一进程依次运行，包含运行时保留内存，不能当成隔离算法的内存比较。此结果不是所有硬件的速度承诺，也不以填满CPU作为成功条件。

### 两场120轮观察与当前局限

| 场景 | 终局路线 | 总体战 | 胜者 | 完整耗时 |
|---|---|---:|---|---:|
| 四方、24星系、`stars-2026` | 世俗／乌托邦／军国／国教各一 | 6 | 暮影议会 | 711秒 |
| 八方、48星系、`adaptive-frontier` | 4军国、2国教、2世俗 | 18 | 翠星联邦 | 1001秒 |

没有指定路线或战争配额。终局有效LRS分别为7/24、30/47座，仍有缺员、断供、低治理和无效命令；四方胜者3座有效LRS覆盖23个星系，座数不等于覆盖。观测后补修了终局扩槽完工检查和库存错误解锁施工重试，仅做针对性及固定快照验证，未追加完整比赛。两场结果不构成长局平衡证明。

## 快速开始

需要 **Node.js 24 或更新版本**、npm 和现代桌面浏览器。

```bash
git clone https://github.com/Kisara-Lab/WAR-In-Stars-AI-compete-game.git
cd WAR-In-Stars-AI-compete-game
npm ci
npm run build
npm start
```

打开 **http://127.0.0.1:8787**。

### 先体验：不需要 API 密钥

1. 点击右上角 **「＋ 新比赛」**。
2. 将 **「控制方式」**切换为 **「纯脚本对战（不调用模型）」**，脚本策略选择 **「智能脚本对战 adaptive-v2」**；也可选择旧脚本基线。
3. 选择4～8方、地图种子和轮数，创建比赛。
4. 点击 **「单轮推进」**仔细观察，或 **「开始比赛」**连续运行。

脚本模式使用内置控制器，不请求模型接口。服务启动会等待操作；默认新局配置是四方模型对战，因此首次无密钥体验请先选择脚本模式。

Windows PowerShell 若拦截 `npm.ps1`，将上述 `npm` 替换为 `npm.cmd`；`npx` 同理使用 `npx.cmd`。

### 再让真实模型上场

将根目录 `AIKEY.env.example` 复制为 `AIKEY.env`：

```powershell
# Windows PowerShell
Copy-Item AIKEY.env.example AIKEY.env
```

```bash
# Linux / macOS
cp AIKEY.env.example AIKEY.env
```

在本机编辑：

```dotenv
base=https://your-provider.example
key=replace-with-your-api-key
```

`base` 可带 `/v1`，后端会归一化地址。新建比赛时选择模型控制器，再为各势力选择接口提供的模型。**游戏界面目前为中文**，英文文档提供完整启动和使用说明。

接口需要支持 **Responses API `/v1/responses`、函数工具调用以及 `stream: true` SSE**。仅支持 Chat Completions 的接口不能直接替代。后端还会查询 `/v1/models`；列表显示不代表每个模型都已验证协议兼容。`grok-4.7` 是实测模型与默认名称，实际可用名称由你的服务商决定。

| 当前5.4决策预算 | 数值 |
|---|---:|
| 每方每轮实际动作 | 最多48条；紧凑批量命令展开后计数 |
| 每方每轮模型请求 | 最多3次，含网络重试与纠错 |
| 单请求超时／总决策超时 | 90秒／180秒 |
| 每个响应输出上限 | 8192 token |
| 推理参数 | `reasoning.effort: low` |

每方通过唯一 `submit_turn` 提交完整计划。一条命令失败，整批资源与动作预留回滚；预算内可修正后重交。任一方没有有效计划，整局暂停，其他势力不会抢先提交。浏览器使用 WebSocket 查看进度，模型传输使用 SSE。

**真实对战会使用你的接口额度。** 界面显示接口返回的 usage；未报告用量会标为未知，不补造 token。精选120轮比赛包含失败重试，共571次请求、66,083,036个已报告token、44次usage未知；这是一场具体比赛的实测值，不是固定运行费用。[模型接入与排错](docs/USAGE.md#模型接口)

## 如何观察这片星海

| 界面 | 用法 |
|---|---|
| 星系群／单星系 | 拖动、缩放星图；双击星系查看行星、基地、航道与舰队 |
| 观察势力 | 在全图与某势力已知情报间切换，查看战争迷雾和情报日期 |
| 国家与行星 | 查看资源、文明路线、福利账单、岗位、设施、施工与造舰队列 |
| 战争与外交 | 查看条约、战争理由、目标控制日数、议和后果和宗教责任 |
| AI决策与事件 | 分别阅读公开战略摘要、工具结果、共同结算事实 |
| 暂停与单轮推进 | 随时停在可保存的轮边界，或只推进一轮 |
| 存档／复盘 | 查看历史轮次、创建独立分支、导出审计JSONL与中文编年史 |

每轮推进100日，内部按十日结算。新局默认规则5.4、存档结构版本5；普通恢复保留原修订，显式升级创建分支。每轮自动保存到 `.data/matches/`，重启后恢复最后完整边界并等待手动继续。

## 从模型意图到世界事实

```mermaid
flowchart LR
    UI[React 观察台] <-->|REST / WebSocket| Server[比赛控制与审计]
    Server --> Boundary[同一轮边界的势力可见情报]
    Boundary --> Models[各方模型并发决策]
    Models -->|Responses SSE| Draft[完整 submit_turn 候选草稿]
    Draft -->|错误结果：预算内重交| Models
    Draft -->|四方或多方全部有效| Sim[主线程统一结算 + worker 局部计算]
    Sim --> Save[原子存档 / 状态哈希 / 编年史]
    Save --> Server
```

星图由种子生成；资源使用定点单位；worker负责局部计算，公共资源与世界状态由主线程汇总。模型不直接修改存档，半截SSE参数不执行。
